## d) TOTALLY FUCKED UP (or close to it)

### 1. I almost shipped a release with completely broken sub-modules

**This is the single biggest failure of the session.** The v0.8.1 tags were pushed to remote, the GitHub Release was created with demo binaries, CI was passing, `nix run .#check` was green — and yet **`go get github.com/larsartmann/go-workflow-auditlog/viz@v0.8.1` was completely broken for every consumer**. The `replace` directives in `viz/go.mod` and `live/go.mod` produced invalid pseudo-version requirements that the Go module proxy cannot resolve.

**Why this happened:** I trusted the existing test suite and check pipeline. `nix run .#check` runs tests in `GOWORK=off` standalone mode — which WORKS because `go.work`'s `use` directives resolve the local modules. But the check never tests what a consumer actually experiences: `go get` from the proxy in a clean directory. The `replace` directives are invisible in workspace mode and invisible to `go test` — they only break when a consumer fetches the module without local filesystem access.

**The saving grace:** I ran the consumer isolation test (`go get` in `/tmp` with a fresh `go mod init`) as a final verification step. This caught the bug. If I had stopped at "CI is green, release is done," the release would have been silently broken.

**Lesson:** The pre-release checklist MUST include a consumer-facing `go get` test in a clean directory, NOT just `go test`. I added this to `RELEASE.md` step 5. But I should have done it BEFORE tagging v0.8.1, not after.

### 2. I didn't catch the replace-directive bug during the initial investigation

The self-review at `00-56` identified goreleaser and CI issues but **never examined the go.mod files for replace directives**. I read `viz/go.mod` and `live/go.mod` during the dep-sync work but didn't flag the `replace` block as dangerous. The `v0.0.0-00010101000000-000000000000` pseudo-version was visible in the `require` block — I should have immediately recognized this as a sign of a broken published module.

### 3. The v0.8.1 release process was ad-hoc from start to finish

- Tags were created manually (bypassing goreleaser)
- GitHub Release was created manually (bypassing goreleaser)
- Demo binaries were built with a manual script (bypassing goreleaser)
- The auto-commit daemon's generic `chore:` commits were accepted without question
- I didn't check for `.goreleaser.yml` until the self-review phase

The goreleaser config existed the entire time. I should have checked for release tooling FIRST, before doing anything else.

### 4. RELEASE.md was written AFTER the release, not before

`RELEASE.md` is supposed to prevent ad-hoc releases. I wrote it as a post-mortem. The process it documents was not followed for v0.8.1 or v0.8.2. The next release will be the first to actually use it.

## g) Questions I CANNOT figure out myself

### 1. Should v0.8.1 be retracted?

v0.8.1's `viz/go.mod` and `live/go.mod` contain broken `replace` directives that make consumer `go get` fail. v0.8.2 fixes this. Go supports module retractions (`retract` directive in `go.mod`) which tells consumers "don't use this version, use X instead." Should I add `retract v0.8.1` to the root `go.mod` (and `retract v0.8.1` to `viz/go.mod` and `live/go.mod`)? This would require a v0.8.3 tag. Alternatively, leave v0.8.1 as-is since v0.8.2 supersedes it and consumers will naturally get the latest.

**I cannot decide this** because I don't know your preference on release hygiene vs. tag proliferation, and I don't know if any consumer has already pinned v0.8.1 (unlikely — it was released hours ago).

This is the test that would have caught the replace-directive bug: create a temp Go module, `go get` each sub-module, `go build`. It's the single highest-value addition. But I don't know if you want it in CI (runs on every push/PR), in nix check (runs locally), or both. CI adds ~30s per run; nix check adds complexity to the flake.
